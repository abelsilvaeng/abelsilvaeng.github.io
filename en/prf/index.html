APIGEO, the geolocation API behind Projeto Mapear

The API that turns a field coordinate into federal highway, kilometer marker, municipality and PRF unit, always against the current official road network.

Projeto Mapear is the PRF program that, since 2003, has identified places along federal highways where children and adolescents are vulnerable to sexual exploitation. It was recognized by the UN Security Forum in 2012. For it to work, every field record has to become a highway, a kilometer marker, a municipality and a responsible unit, consistent with the official network.

  • Designed and built the API in FastAPI on PostGIS, with two services: lookup by coordinate and lookup by state, highway and kilometer.
  • Modeled the spatial database with the national road network (SNV, from DNIT, Brazil's federal transport infrastructure agency), IBGE municipal boundaries and PRF operational units.
  • Automated the data updates: each new release is detected, downloaded, loaded, validated inside the database and switched on in a single transaction.
  • Put load quality control inside the database: a failed load never goes live and the current release stays in place.
  • Designed the cache with a key versioned by all three datasets, so a release switch never serves a stale answer.
  • Validated responses field by field against reference records and shipped the API through the corporate gateway and CI/CD pipeline.
  • Proximity queries on geography with a GiST index, in SIRGAS 2000
  • Linear referencing: snapping the point to the road segment and interpolating the kilometer
  • Stable-name views over one table per release, with transactional switch
  • Load validation by volume, reference system, state coverage and geometry
  • API in production at PRF, used by Projeto Mapear.
  • Automatic updates in place for the road network, municipal boundaries and operational units.
  • Mapear in public numbers: running since 2003; 11th edition in 2025/2026; 13,758 mapped locations; 4 risk levels. Source: the project's official page.
  • The awards and honors belong to the project, which is over 20 years old. The API is my technical contribution to it. No mapped location is shown here.

Critical road segments: observed risk and latent risk

A lab built on PRF open data that crosses crashes with speeding violations, kilometer band by kilometer band, to find where the two risks overlap.

A crash shows where risk has already materialized. Speeding shows where it is still latent. Looked at separately, each draws a different map. The lab uses open data only and answers one question: on which road segments do the two risks coincide?

  • Loaded the open crash data (2007 to 2026) and the speeding violation data into a lab PostGIS database.
  • Handled the traps that silently break the analysis: column order that changes between years, coordinates only from 2017 on, inconsistent highway codes.
  • Placed violations that have no coordinate on the map by linear interpolation along the road segment, the same logic as APIGEO.
  • Split the network into 10, 20 and 30 km bands and built a combined index of crashes, fatalities and speed.
  • Built other products on the network: kernel density of crashes, coverage by network routing, exposure per vehicle-kilometer and pavement condition.
  • Documented each product starting from the question and the decision, and labeled anything that is a simulated scenario.
  • Linear segmentation by kilometer and interpolation along linear references
  • Percent ranking and a composite index, with weights still exploratory
  • Kernel density estimation
  • Dijkstra routing on a topological network (pgRouting)
  • Exposure normalization: crashes per vehicle-kilometer
  • About 2.2 million crash records from PRF open data, 2007 to 2026, organized in a spatial database.
  • Critical-segment service and demo portal running in the lab.
  • A write-up of the data traps found and how each one was measured.
  • This is a lab: there is no operational use to report, and no real segment is shown.

Corpus for an on-premises RAG assistant

I prepared a legal and administrative HR collection to become the knowledge base of an assistant running on an in-house generative AI platform.

The assistant looks up HR regulations using a RAG architecture on an on-premises generative AI platform. The collection came as PDFs, DOCX files, spreadsheets and images, with text corrupted during extraction. In legal RAG, broken text and repealed rules turn into wrong answers. My part was the corpus, not the application.

  • Took part in planning and structuring the project, defining build scopes and what would be done in Python.
  • Wrote the extractor that converts PDF, DOCX, spreadsheets, images and HTML to Markdown.
  • Traced the corrupted text to typographic ligatures in the fonts, not to encoding, and built a word-context fix.
  • Set up image description with a local vision model, leaving the source document untouched.
  • Built chunking that follows legal structure: article, paragraph, items and sub-items stay together.
  • Classified each rule by type and legal status, so the assistant does not answer with a repealed rule.
  • Context-based normalization of ligatures mapped to Unicode private use area
  • Chunking on legal anchors, with validity metadata
  • Image description by a locally run vision model
  • Completeness checks and validation cycles until nothing was left pending
  • Preparation pipeline completed, with the final validation cycle free of errors.
  • Ligature fix documented and reusable for other federal agency document collections.

API validation, load and sizing protocol

A reusable protocol that answers four questions together: what changed in the contract, what the API gets wrong, how much load it holds and how much database that takes.

It grew out of APIGEO: we needed to show the API answered correctly and held up under load. A load test alone measures how fast a possibly wrong answer comes back; validation without load misses connection exhaustion; and neither tells you whether throughput is headroom or ceiling without the database parameters.

  • Wrote the protocol in five steps: contract, database parameters, functional validation against known answers, load ramp and a consolidated report.
  • Built the suite to be API-agnostic: switching APIs means switching target files, not code.
  • Set the reporting principles: the criterion is stated next to the number, a skipped step shows up as a gap, the baseline is explicit.
  • Set up containerized scenarios to separate the effect of worker count from the effect of architecture.
  • Generated reports for the requesting teams and for the security team from the results.
  • Stepped load ramp, with cold and warm cache
  • Latency percentiles (p90, p95) with the network floor measured and subtracted
  • Stratified systematic sampling that preserves the distribution by state
  • Little's law to estimate concurrency and size connections
  • Field-by-field validation against known answers
  • Protocol and suite documented and reusable.
  • Used to validate APIGEO across environments and versions.
